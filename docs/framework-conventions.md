# Framework conventions

The rubric the **Codegen** and **Review** agents are held to. Every review finding must cite a rule
id from this file. If this file says nothing about something, the reviewer says so under
`conventions_silent_on` instead of making up a rule. A human then decides whether to add one
(C-AGENT-9).

Rule ids are stable. Once a rule is removed, its id is never reused.

---

## Test cases & traceability

- **C-TC-1** A test case lives in `test-cases/<ID>.md` (IDs are `TC-UPLOAD-NNN`) and is the only
  definition of *what* to test. The knowledge file is the only definition of *how* the page
  behaves. When the two disagree, the agents never edit the test case. The disagreement goes to
  Doc-Gap.
- **C-TC-2** The test is titled `<ID>: <test case title>` and tagged `@tc:<ID>` plus at least one
  area tag (`@upload`, `@smoke`). `npx playwright test --grep @tc:<ID>` must select exactly that
  test.
- **C-TC-3** Every step that has an expected result maps to an assertion. If a step is not
  automated, the batch report must say why. Skipping it silently is a blocker.
- **C-TC-4** One spec file per test case, named `<ID>-<short-slug>.spec.ts` (e.g.
  `tests/upload/TC-UPLOAD-001-upload-form.spec.ts`), so the file sorts by ID and matches
  `test-cases/<ID>.md`. When a file is renamed or moved, grep the whole repo for the old path and
  update every live reference. Dated records (review logs, past self-verify runs, doc-gaps
  sections) are left as written.

## Locators

- **C-LOC-1 (default)** `getByRole(role, { name })`, `getByLabel`, `getByText`. These match what
  a user and a screen reader perceive.
- **C-LOC-2 (fallback)** If an element has no usable accessible name, use a stable DOM `id`
  from the page (e.g. `#file-upload`), with a comment saying why role/name was not usable.
- **C-LOC-3 (last resort)** Use any other CSS only with a comment saying why. Never identify an
  element by colour, computed style or DOM position.
- **C-LOC-4** Every locator in `pages/` must trace to an entry in `knowledge/pages/*.yaml`.
  `npm run knowledge` checks this mechanically.
- **C-LOC-5** No raw `page.locator()` / `getBy*()` in a spec. Locators belong in the page object,
  so a spec reads as user intent.

## Waiting

- **C-WAIT-1** No fixed sleeps (`waitForTimeout`) anywhere in this repo. The assertion is the
  wait.
- **C-WAIT-2** Prefer web-first assertions (`await expect(locator).toHaveText(...)`) over reading
  a value and comparing it. A web-first assertion retries until it passes or times out; a value
  read with `textContent()` is a single snapshot that can be taken too early.

## Assertions

- **C-ASSERT-1** Assert the whole value when the whole value is the requirement. Use
  `toHaveText('exact')`, not `toContainText` on a fragment, unless the knowledge file shows the
  text contains whitespace or other content that varies. Locators may match a name loosely
  (`getByRole` without `exact: true`), so the exactness lives in the assertion: a core outcome is
  checked with `toHaveText`, never with `toBeVisible` on a named locator alone.
- **C-ASSERT-2** Pair an absence assertion with a presence assertion. On its own,
  `not.toBeVisible()` also passes when the page failed to load.
- **C-ASSERT-3** Wrap each phase in `test.step()` so the HTML report reads as a narrative.
- **C-ASSERT-4** Assert the outcome the user sees *and* the server's answer where both exist.
  For example, await the `POST /upload` response and check its status, then check the page.
  A heading alone can be served by a cached or error page.
- **C-ASSERT-5** To show that an action sent **no** request, count matching requests with a
  listener started *before* the action, filtered to the exact method and URL (so third-party
  beacons can't affect it). Assert the count is 0 at that point, then assert the running total
  again after a later action known to send one (for example `1` after submit), so a request
  fired late by the first action still shows up. Do not use a negative `waitForRequest` with a
  timeout: it is slow and only covers its own timeout window.

## Files (upload)

- **C-IO-1 Upload a COMMITTED fixture.** Files live in `tests/fixtures/files/` and are tiny,
  harmless and generated by us. Never upload anything from the tester's machine. This is a
  **public** server, and anything uploaded to it is effectively published.
- **C-IO-2 Arm the event before the action.** Use `Promise.all([page.waitForResponse(...), click])`
  or `page.waitForEvent('filechooser')` before the click, never click-then-wait.
- **C-IO-3 Name the upload path you are testing.** `setInputFiles` on the `<input type=file>` tests
  the form. It does **not** test the drag-and-drop zone. A drag-and-drop test must dispatch a real
  `drop` event carrying a `DataTransfer` on the drop target. A test that calls `setInputFiles` and
  calls itself "drag and drop" is a correctness blocker.

## Known defects (the deliberately failing test)

- **C-DEFECT-1** A test that asserts the *specified* behaviour where the app is known to
  do something else is tagged `@known-defect`, and it **fails, red**. Do not use `test.fail()`
  or `test.fixme()`. `test.fail()` reports a known defect as a pass, and this suite's brief asks
  for the failure output to be visible.
- **C-DEFECT-2** The test's title or a `test.info().annotations` entry names the defect, and the
  test links to its `reports/doc-gaps.md` entry. Anyone reading the red result must be able to
  tell from the report alone that the failure is expected, and why.
- **C-DEFECT-3** A known-defect test must still prove it *can* pass. Its self-verify replaces
  the inversion step (C-AGENT-4) with a run against a `page.route()` stub that returns the
  specified behaviour. The test must pass against the stub, which proves the assertion is a
  real check and not `expect(false)`. The stub is a verification tool. It is never committed in
  the spec's default path.
- **C-DEFECT-4** The assertion must fail *on the defect*, not on something incidental. The failure
  message must show the defect (e.g. a `500` status or `Internal Server Error`), not a locator
  timeout on an unrelated element.

## Page objects & fixtures

- **C-POM-1** One page object per screen in `pages/`. Methods are named for user intent
  (`uploadFile(path)`, `submitEmpty()`), not for mechanics (`clickButton2()`).
- **C-POM-2** Specs get page objects from the fixture in `tests/fixtures/index.ts`
  (`test('…', async ({ uploadPage }) => …)`), never with `new UploadPage(page)` in a spec.
- **C-POM-3** A page object exposes locators as `readonly` properties, so specs can make
  web-first assertions on them. Page objects do not contain `expect`, except in a method whose
  name says it waits for a state (`expectLoaded()`).
- **C-POM-4** Reuse before you create. Extend the existing page object. Do not add a second way
  of doing the same thing.
- **C-POM-5** A page object may hold an observation helper, such as a request counter, alongside
  its locators. It follows C-POM-3 (it returns values and never asserts), and it must not leak.
  Any `page.on(...)` listener it adds is removed, either by a disposer the helper returns or in
  the fixture's teardown.

## Knowledge files

- **C-KNOW-1** There is one canonical directory, `knowledge/`.
- **C-KNOW-2** Every line traces to something the Explorer saw. If nothing was seen, write
  `NOT YET OBSERVED`.
- **C-KNOW-3** Every locator has a `why:` that explains the choice.
- **C-KNOW-4** `gotchas` holds anything that cost time, together with the fix.
- **C-KNOW-5** Record contradictions under `doc_discrepancies`. Do not resolve them.
- **C-KNOW-6** `covered_by` lists the tests that depend on the file, so a change to the page tells
  you what to re-run.
- **C-KNOW-7** Keep `last_observed` current.

## Agent obligations

- **C-AGENT-1 Separation of powers.** The Explorer is the only agent that may open a browser.
  Codegen works from knowledge files alone, so it cannot guess a selector.
- **C-AGENT-2 `blocked: needs_exploration` is a success.** If the knowledge does not cover a
  step, Codegen stops and names the missing fact.
- **C-AGENT-3 Context budget.** An agent loads the test case, the scenario-map entry and 1–3
  knowledge files. It never reads the whole repo "to get oriented".
- **C-AGENT-4 Self-verification is mandatory.** Run the test (pass), **invert one core assertion**
  (fail), revert (pass). Record each run in words in the batch report. For known-defect tests,
  see C-DEFECT-3.
- **C-AGENT-5 Record what was NOT generated, and why.**
- **C-AGENT-6 Review covers both code and knowledge files**, with a separate checklist for each.
- **C-AGENT-7 A reviewer follows this rubric, not a persona**, and produces findings, not fixes.
- **C-AGENT-8 Doc-Gap classifies, proposes and never publishes.** It uses four categories:
  contradiction, missing coverage, stale, and unverifiable scenario. An unverifiable scenario is
  always escalated to a human.
- **C-AGENT-9 Escalate rubric gaps; never invent rules.** Any rule raised in more than two
  reviews means the Codegen prompt or this file needs to change, not the code.
- **C-AGENT-10 No new dependencies.** The suite depends only on Playwright, TypeScript and
  `@types/node`.
